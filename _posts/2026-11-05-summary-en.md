### [Moonshot releases open weights for Kimi K3.1 Pro](http://platform.kimi.ai/) ⭐️ 9.0/10

Moonshot AI published open weights for Kimi K3.1 Pro on Hugging Face, describing it as a native multimodal agent model with 2.8T total parameters, 104B active parameters, and roughly 1M tokens of context; it is the first model in the K3.1 series. The weights are released in MXFP4 quantized form, and Moonshot also offers an API at platform.kimi.ai under the model name kimi-k3.1-pro that is compatible with OpenAI and Anthropic interfaces. The release is reported in a single Telegram post, so the parameter and context figures are vendor claims that have not been independently verified here.

telegram · zaihuapd · Nov 4, 15:47

**「Background」** Kimi K3.1 Pro is the first model in Moonshot AI&\#x27;s K3.1 series, post-trained from the earlier Kimi K3 with large-scale joint reinforcement learning across hundreds of downstream domains, according to its Hugging Face model card. Kimi K3 itself was released as open frontier weights under the Kimi K3 License, supporting text, images, and video within a single model and a 1-million-token context window. The K3.1 Pro release therefore extends an existing open-weight line rather than introducing a new one.

**「Practical impact」** The MXFP4 weights are large enough that local deployment is impractical for most users; one commenter estimated the download at about 1453GB and said running it would need something like an 8x B300 node. Third-party providers are already listing the model, with OpenRouter hosting it, so most developers will likely reach it through hosted APIs rather than self-hosting.

**「Community discussion」** Commenters disagreed on how the model compares to rivals: one argued it does not clearly beat DeepSeekV4.1-Flash and called it &quot;benchmaxxed,&quot; while another said their own testing did not show that pattern and described it as a strong open release somewhat behind the frontier but useful for most cases. A separate thread focused on inference economics, with one commenter reporting that Together and Modal showed higher throughput than Moonshot&\#x27;s own endpoint at the same price, suggesting room for providers to optimize costs.

### [OpenAI pipeline reports 948 Linux privilege-escalation exploits](https://openai.com/index/a-thousand-fewer-paths-to-root/) ⭐️ 9.0/10

OpenAI says its autonomous vulnerability-research pipeline reproduced 1,724 Linux kernel vulnerabilities in a single October 2026 scan and generated 948 working local-privilege-escalation exploits that let a low-privilege local user gain root, plus 291 information-leak proofs of concept. The company reports at least 10 novel exploitation techniques, which it says third-party experts confirmed as new, including a new persistent resilient object for cache spraying, a new page-grooming method, a new data-only privilege-escalation/arbitrary-write technique, and arbitrary type confusion. OpenAI puts total API cost at $1,213,430, or about $1,279 per successful LPE exploit \(roughly $359 per exploit actually developed\), and estimates the exploits would be worth $18.9M–$66.3M at historical Pwn2Own/TyphoonPWN bounty levels. These are vendor claims from OpenAI&\#x27;s own announcement, not independently measured results.

The claims come from OpenAI&\#x27;s own post and press coverage of it, not from an independent audit of the kernel.

**「Why it matters」** If the counts hold, the pipeline shows that automated agents can turn kernel bug reproduction into working root exploits at a per-exploit cost well below typical bounty payouts, which shifts the economics of both offensive research and defensive triage. ### [Anthropic Reports Progress on Cryptographically Provable LLM Inference](https://www.anthropic.com/research/provable-inference) ⭐️ 8.5/10

Anthropic published research on cryptographically provable inference for large language models, aimed at letting a client verify which weights a provider actually ran. The scheme uses a commitment of roughly 6.5 MB that is valid for about 16 million requests before the provider must recommit, plus one proof per request; checking a proof takes 17 seconds on 24 threads and 21 seconds on a single thread, including the offline-phase check. The reported cost is a 90–100x compute overhead, and the work is presented as research progress rather than a deployed service. Commenters note the approach builds on prior work, including the VerInf project, and question attribution.

hackernews · ltononro · Nov 4, 17:17 · [Discussion](https://news.ycombinator.com/item?id=50368626)

**「Background」** The community discussion points to VerInf, an open project that produces zero-knowledge proofs of LLM inference and has proven a 400B-parameter model with the prover running on a single consumer NVIDIA DGX Spark, using only hash-based commitments with no trusted setup. A commenter, neuwirth, says Anthropic&\#x27;s work builds on VerInf and disputes the attribution. Separately, a May 2026 survey of verifiable AI inference describes a forensic approach that achieves bit-identical reproducibility across controlled local inference runs by hashing model artifacts and logging inference-time seeds.

**「Practical implications」** The reported overhead—roughly 90–100x compute for proving, with proof checking taking about 17 seconds on 24 threads—makes per-request verification impractical for high-volume serving, so the approach is better suited to spot checks or audit scenarios than routine use. Because the proof hides weights and intermediate values but not the model architecture, providers can demonstrate that a committed model produced an output without revealing proprietary parameters, though the commitment must be renewed after about 16 million requests.

**「Community Discussion」** Commenter neuwirth said the work builds on VerInf, their own project as a MARS fellow, and that Anthropic adopted design choices such as the 400B Maverick model with little attribution. nemo1618 argued that for open-weight models provable inference is trivial by re-running the computation deterministically, which is cheaper than zero-knowledge proofs, while vessenes said a probabilistic proof from four independent providers running the same non-batched prompt would be cheaper than the 90–100x compute hit. vintagedave raised the practical case of catching providers that route requests to a different model than the one named.

The model incorporates base-pairing information from secondary structure into sequence pretraining and was trained on roughly 21 million sequence-structure pairs, with the team reporting state-of-the-art results across multiple tasks. The team also developed MUSES, a method that integrates multiple secondary-structure predictions to reduce bias, and a 3D structure prediction module called Zfold, whose performance the team reports as comparable to AlphaFold 3. **「Impact」** Because the data, weights, and code are openly released, RNA and structural-biology researchers can directly evaluate structRFM and the Zfold module rather than reimplementing them from the paper. The reported AlphaFold 3 comparison is the team&\#x27;s own claim and has not been independently verified in the supplied material.

### [Developer Adds Co-op Multiplayer to DOS Wing Commander After Decade of Reverse Engineering](https://fireflyk64.github.io/wcmulti/) ⭐️ 8.0/10

A developer has documented a ten-year reverse-engineering effort that enables co-op multiplayer in the DOS version of Wing Commander, allowing players to fly the story missions together. The work involved probing game memory to locate state variables, injecting calls into game functions, and synchronizing game state across a network. The author says the project began in 2015 after noticing the game state fit within the 64k data segment, and that the camera lives in an entity structure. The documentation describes the approach but does not state a release date or distribution method.

hackernews · daniel\_rh · Nov 4, 18:51 · [Discussion](https://news.ycombinator.com/item?id=50369895)

**「Context」** Wing Commander, released by Origin Systems in 1990, is a DOS space-combat game with no built-in multiplayer. Reverse engineering such games typically involves observing memory changes during gameplay to identify variables and then modifying or hooking the running program. The author&\#x27;s approach builds on that practice by injecting calls into existing game functions and synchronizing the resulting state over a network.

**「Impact」** The technique is specific to the DOS build of Wing Commander and depends on the game state fitting in a 64k data segment, so it is not a general multiplayer solution for other titles. Players interested in co-op would need to run the documented setup rather than an official patch, and the source does not describe compatibility with other versions or emulators beyond DOSBox.

**「Community Reaction」** Commenters asked whether the approach could be reused to build a similar game and why the author used the data channel rather than the RTC stream for voice. Another commenter described earlier memory-editing techniques for identifying game variables, framing the project as a continuation of that practice.

### [Go Introduces New encoding/json/v2 API](https://go.dev/blog/jsonv2) ⭐️ 7.5/10

Go&\#x27;s official blog introduced a new encoding/json/v2 API, a redesign of the standard library&\#x27;s JSON package. The post prompted community discussion focused on migration tradeoffs, particularly the removal of MarshalIndent, which commenters say makes dumping readable JSON much harder. The source provides no version number, release date, or compatibility details, so the API&\#x27;s shipped status and availability remain unconfirmed.

hackernews · olexsmir · Nov 4, 17:52 · [Discussion](https://news.ycombinator.com/item?id=50369106)

**「Background」** Go&\#x27;s original encoding/json package, which implements JSON encoding and decoding as defined in RFC 7159, has long been the standard library&\#x27;s default JSON API. The new encoding/json/v2 package is described in Go&\#x27;s migration guide as a major revision of that original package, introduced in Go 1.27, and the guide states that migrating from v1 is optional. The v2 documentation also notes that both versions may still lose precision when unmarshaling into an \`any\` interface value, since unmarshal uses a float64 by default to represent a JSON number unless a custom unmarshaler is supplied.

**「Impact」** Developers migrating existing code will need to rewrite calls that relied on MarshalIndent, since commenters report the v2 equivalent is considerably more complex and non-obvious. Teams should check the blog post for the exact replacement pattern before upgrading.

**「Community Discussion」** Commenters broadly welcomed the redesign, but CamouflagedKiwi argued that dropping MarshalIndent makes quick, readable JSON dumps painful to migrate. Others noted that no JSON5 implementation yet builds on encoding/json/v2, and one commenter described using AI models to write Go code while still valuing the language&\#x27;s performance and safety.
